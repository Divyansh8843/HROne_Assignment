# REVIEW.md

Every defect found in the starter `app/main.py`. Fixed in the rewritten implementation.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `list_employees` / line 93 | Pagination skip uses `page * page_size` instead of `(page - 1) * page_size`. Page 1 would skip the first 20 results, returning nothing or wrong data. | `GET /employees?page=1&page_size=20` returns an empty list when 20 employees exist. | Changed to `skip = (page - 1) * page_size` — standard zero-based offset. |
| 2 | `list_employees` / line 94 | `total` is always `count_documents({})` (unfiltered) instead of `count_documents(q)`. A department filter produces a wrong total. | `GET /employees?department=Sales` returns `total=100` when only 5 Sales employees exist. | Changed to `db.employees.count_documents(q)` so total always reflects the applied filter. |
| 3 | `list_employees` / line 95 | Results are not sorted by `emp_code` ascending as required by the contract. The `.find()` uses no `.sort()`. | List order is insertion order (undefined), failing any ordering assertion. | Added `.sort("emp_code", ASCENDING)` to the cursor. |
| 4 | `punch_in` / line 102 | `datetime.fromtimestamp(ms / 1000)` converts milliseconds using the local system timezone, not UTC. On any server not in UTC the attendance date and late_minutes will be wrong. Also, the value is not truncated to whole seconds. | On a UTC+5:30 server, a UTC midnight punch (epoch 1783296000000) resolves to the previous IST calendar date. | Changed to `datetime.fromtimestamp(ms // 1000, tz=UTC)` with integer division to truncate. |
| 5 | `punch_in` / line 103 | `ts.date()` uses local-timezone date, not IST. The attendance date `d` is derived from the naive datetime, which may disagree with IST. | A punch-in at 23:00 UTC (04:30 IST next day) would record the wrong date. | Derive the IST calendar date via `dt_to_ist(punch_utc).date()` and apply R1 overnight-shift logic. |
| 6 | `punch_in` / line 104–105 | Duplicate check is a race-prone check-then-insert (two requests can both pass the `find_one` check and both succeed). The contract requires: "concurrent duplicate creates must yield exactly one 201". | Concurrent requests for the same employee/date both return 201 and create two records. | Removed the pre-check entirely; rely on the unique compound index `(emp_code, date)` and catch `DuplicateKeyError` from `insert_one`. |
| 7 | `compute_late_minutes` / line 36–37 | `start = punch_in.replace(hour=h, minute=m, ...)` builds the shift-start on the punch-in's datetime object without setting a timezone. Comparison of a timezone-aware `punch_in` and a naive `start` raises a `TypeError`. Also, the grace-period check is `> 10` (minutes, off by one): a punch at exactly 10 minutes after shift_start should be **not** late (grace ≤ 10:00), but the code returns 10. | 09:40:00 → should return 0; code returns 10 (wrong). 09:40:01 → should return 10; code raises TypeError with aware datetimes. | Rebuilt `compute_late_minutes` to construct the shift-start as a timezone-aware IST instant and compare `diff_sec <= 600`. |
| 8 | `compute_overtime` / line 46 | `datetime.fromisoformat(date_str)` creates a naive datetime, then `.replace(tzinfo=IST)` is applied. For an overnight shift the shift_end should be placed on `attendance_date + 1`, but the function doesn't account for this. Also, any punch_out below 30 minutes of overtime is still counted. | A punch-out 20 minutes after shift end returns `overtime_minutes = 20` (should be 0). Overnight shift overtime is off by one day. | Rewrote as `compute_overtime_minutes_with_start` which adds `timedelta(days=1)` for overnight shifts and applies the 30-minute minimum threshold. |
| 9 | `health` / line 73–74 | Returns `{"status": "ok"}` unconditionally without pinging MongoDB. The contract says: "Returns 200 only if MongoDB answers a ping, otherwise 503." | With MongoDB stopped the health endpoint still returns 200, so the runner waits for a healthy server that never becomes ready. | Added `client.admin.command("ping")` inside a try/except; raises HTTP 503 on failure. |
| 10 | `list_attendance` / lines 144–145 | `docs = list(db.attendance_logs.find(q))` loads the **entire** collection into Python memory before sorting and paginating. The contract requires it to "stay fast on a collection of ~100,000 records; do not load the collection into memory". | With 100 000 records every call OOMs or times out. | Replaced with a server-side `.sort().skip().limit()` cursor and `count_documents(q)` for the total. |
| 11 | `create_employee` / line 82 | `datetime.now()` returns a naive datetime (no timezone). The data model says `created_at` is a BSON date (UTC). Storing a naive datetime may cause timezone confusion when read back. | On a non-UTC system the timestamp stored is local time, not UTC. | Changed to `datetime.now(UTC)` so the stored value is unambiguously UTC. |

## Items examined and confirmed NOT defective

- `compute_work_hours`: the formula `(punch_out - punch_in).total_seconds() / 3600` is correct; `round(..., 2)` is the only concern (banker's rounding risk), addressed in the new implementation with `half_up_round`.
- `EmployeeIn` / `PunchInIn` Pydantic models: the field declarations themselves are fine; the missing validators are an omission (addressed in the new code) rather than a defect in what's there.
- The module import order and `load_dotenv()` call are correct.
